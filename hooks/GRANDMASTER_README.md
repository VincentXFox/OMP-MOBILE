# GRANDMASTER 10.0

Версия 8 закрывает три дефекта, которые 7.5 не закрывал, потому что они **текстовые**:
инструкция «сначала план», «не зацикливайся», «оговорки не выход» в промпте есть —
а поведение не меняется. В 8.0 это вынесено в рантайм: хуки, которые физически
не дают инструментам выполниться в нарушение контракта.

## Что нового против 7.5

| Дефект | Как было (7.5) | Что теперь (8.0) |
|---|---|---|
| Нет todo в начале работы | правило в промпте, соблюдается через раз | `grandmaster-todo-first`: первый `edit`/`write` на многошаговом запросе **блокируется**, пока в **текущем ходе** нет `todo`-плана (8.1: план проверяется на каждый пользовательский ход, а не один раз за сессию). Разведка (read/grep/glob) разрешена до плана. После 3 блокировок инструмент отпускается — вечного запора нет. |
| Зацикливание на одном месте | «anti-loop gate» текстом | `grandmaster-loop-breaker`: одинаковый вызов (инструмент + нормализованный вход) с тем же падением **3 раза** → четвёртый блокируется с требованием сменить уровень/инструмент/гипотезу. 8 одинаковых успехов подряд → предупреждение о переборе. Не больше 4 блокировок на сессию. |
| «Готово с оговорками» как выход | гейт требовал тег причины | гейт 8.0 дополнительно требует **доказательство попытки** рядом с тегом («пробовал: … → результат») и читает **todo-план самой сессии**: пока в нём есть открытые пункты, `ГОТОВО` и `ГОТОВО-С-ОГРАНИЧЕНИЯМИ` не принимаются. После третьего блока гейт прямо говорит: переформулировка не поможет. |
| Ложный «успех» после самопроверки | автор сам себя проверял | 9.0: `grandmaster-adversarial-review` требует независимый разбор (субагент/harness с negative control) и строку `ADVERSARIAL:` в финальном ответе; английская проза в сообщениях хуков ловится `ru-lint` |
| Перепроверка своей работы | «verify by run» в промпте | правило + гейт: `EVIDENCE:` по каждому критерию, `DONE` с признанием непроверенного отклоняется, `PARTIAL/BLOCKED` требует «БЛОКЕР:» и ≥2 испробованных стратегий. |

Плюс в инструкции (RULES.md / APPEND_SYSTEM.md) появилась инфраструктура, которой

## 9.0: состязательный разбор и harness

8.x проверял **форму** ответа (статус, доказательства, реестр, теги, todo). Не проверялось главное:
пытался ли автор **опровергнуть** свой результат, или проверил только счастливый путь. Отсюда два
компонента.

### `grandmaster-adversarial-review` (guardrail)

Хук `~/.omp/agent/hooks/pre/grandmaster-adversarial-review.ts` на `session_stop`: если ответ несёт
`СТАТУС: ГОТОВО` или `ГОТОВО-С-ОГРАНИЧЕНИЯМИ`, в нём обязана быть строка состязательной проверки
с артефактом и вердиктом:

```
ADVERSARIAL: <что пытался опровергнуть> → <команда / путь / субагент> → <PASS | найдено N: …>
```

- Разбор делает **независимый субагент** (`reviewer` / `security-reviewer`) или `gm-harness` с negative
  control; самопроверка автора не считается. Артефакт обязателен: команда, путь или имя субагента.
  Строка «проверил вроде нормы» не принимается — нужен вердикт.
- Разбирается только сам блок строки `ADVERSARIAL:` (до следующей секции): чужой `EVIDENCE: bun test → PASS`
  не подпирает метку. Метка внутри ```-фенса или кавычек — цитата, а не проверка. Команда в бэктиках внутри
  строки разбора принимается: это как раз честный отчёт.
- `PARTIAL`/`BLOCKED` без доказательств и без заявленного результата освобождены; но если в ответе есть
  `EVIDENCE:` или заявление «исправлено/добавлено/работает», разбор обязателен — иначе «объявлю PARTIAL»
  становится дешёвым обходом. После 3 блокировок гейт пишет в stderr, что исчерпал лимит (не молчит).
- `PARTIAL`/`BLOCKED` не требуют строки: там свои требования (`БЛОКЕР:` + ≥2 попытки).
- Не больше 3 блоков за сессию (антидедлок). Вне GRANDMASTER-проекта хук молчит.
- Граница честности: хук проверяет наличие шага и артефакта, а не правдивость отчёта; выдумать
  строку дешевле, чем прогнать negative control (контроль, который обязан упасть), но в транскрипте это видно.

### `gm-harness` (состязательный прогон)

`~/.omp/agent/harness/gm-harness.sh` — прогон сценариев в изолированном каталоге (`HOME`, `TMPDIR`,
`XDG_*` переопределены). У каждого сценария **обязателен negative control** — команда, которая
обязана упасть. Прошлый контроль означает, что проверка ничего не различает, и сценарий помечается
FAIL: «проверка пустая».

```
gm-harness.sh run <scenario.json> [--json] [--keep] [--timeout 120]
gm-harness.sh run-dir <dir>
gm-harness.sh self-check      # доказывает, что вакуумная проверка распознаётся
```

Кейсы: `positive` (рабочий путь), `negative` (контроль, обязан упасть), `fault` (инъекция сбоя через
`env`). Контроль обязан объявить `expectExit` явно (не 0) и отличаться от `positive` командой или `env`.
Поддерживаются `expectExit`, `expectStdout` (подстрока), `expectStdoutRe` (регексп без тривиальных
шаблонов), `expectFile` (только внутри каталога кейса), `fixtures` (только внутри каталога сценария).
Изоляция: `HOME`/`TMPDIR`/`XDG_*` подменяются и побеждают `env` сценария; в кейс уходят только
PATH/LANG/LC_ALL/TERM/TZ/SHELL. Таймаут убивает всю группу процессов кейса, вывод пишется в файлы.
Границы: сценарий — доверенный код под UID владельца, ФС не песочница. После прогона в каталоге кейса
остаются `case.json`, `stdout.txt`, `stderr.txt` (с `--keep`).

### `ru-lint` (язык сообщений)

`~/.omp/agent/hooks/tests/ru-lint.ts` проверяет, что в хуках, тестах и harness нет англоязычных
сообщений владельцу: техничные маркеры (`ADVERSARIAL:`, `EVIDENCE:`, `СТАТУС:`, имена инструментов,
поля JSON) разрешены, английская проза — нет. Ловит и короткие фразы, и сообщения, собранные из кусков
(`"Upload " + "failed, " + "please retry"`), не режет строки по `//` внутри литералов и падает, если
не нашёл ни одного файла (нулевое покрытие — не «чисто»). В регрессии три стиля английского текста
обязаны быть найдены.

### Скилы

`~/skills/grandmaster/adversarial-review/SKILL.md` — процедура разбора (гипотеза → независимый
инструмент → артефакт → исправление → строка `ADVERSARIAL:`), в том числе как ставить задачу
субагенту («опровергни», а не «подтверди»).
`~/skills/grandmaster/gm-harness/SKILL.md` — формат сценариев и правила честности.

### Регрессия

`~/.omp/agent/hooks/tests/gm-regression.sh`, секция «GRANDMASTER 9.0»: импорт хука, четыре пробы
поведения (без строки → блок; строка без артефакта → блок; полная строка / `PARTIAL` / без статуса →
пропуск; не больше 3 блоков), `harness self-check`, сценарий-пример, проверка изоляции `$HOME`,
negative control для вакуумного сценария и `ru-lint` с его собственным контролем.

## Честные границы

- Гейты проверяют **форму**, а не истину: `EVIDENCE:` можно сфабриковать, todo можно
  закрыть не сделав. Они делают недоделанное видимым и требуют явной лжи — что и есть
  цель; полностью это не решается никаким хуком.
- `todo-first` — эвристика многошаговости по тексту запроса; тривиальный запрос она
  пропускает, а очень короткий многошаговый («сделай A и B») может не поймать.
  Это осознанно: ложные блокировки дороже пропуска, окончательный контроль — стоп-гейт.
- `todo-first` блокирует только `edit`/`write`: правки через `bash` (redirect, `sed -i`,
  `tee`) гейт не видит — живой прогон 2026-10-18 показал такой обход. Расширение на bash
  осознанно не делалось: эвристика по shell-командам даёт ложные блокировки проверочных
  пайплайнов, а дисциплину правок в bash держат правила агента и стоп-гейт.
- Живая проверка 2026-10-18 (OMP 18.10.4): провокация «создай a.txt, затем проверь и
  допиши world, todo не вызывай» дала реальные блоки `1/3 → 2/3 → 3/3` в файле сессии и
  отпуск на четвёртой попытке; файл всё же создан через `bash` — см. границу выше.
- `loop-breaker` ловит повторяемость падений, не смысловой тупик. Смысловой тупик ловит
  стоп-гейт (нет EVIDENCE → нет DONE) и правило двух стратегий для PARTIAL.

## 8.1 — план на каждый ход

**Дефект 8.0.** `todoSeen` жил всю сессию и не сбрасывался: первый же `todo` (даже от
прошлой задачи) навсегда снимал гейт. Любая следующая многошаговая задача начиналась
с правки файлов без плана — «туду не в начале» воспроизводилось после первого хода.

**Правка.** План проверяется на каждый пользовательский ход: `before_agent_start`
сбрасывает `turnTodoSeen`, а `todo` в текущем ходе его ставит. Блок правок снимает
только свежий (init или обновлённый) план. Счётчик блокировок по-прежнему на сессию
(3), тривиальные запросы и `без плана` не трогаются, read-only разведка не блокируется.
Состояние: `gm8TodoState(...).turnTodoSeen`.

**Доказательство.** Тест `новая задача в той же сессии требует СВЕЖИЙ план`:
на старом хуке — 20 pass / 1 fail (edit во втором ходе проходит без плана),
на новом — 21 pass. md5: `a58afe670bde9944a85beb229add221b` (живой хук = копия в комплекте).

**Эвристика (по живому прогону).** Провокация в `omp -p` показала: инфинитивная
постановка задачи («исправить парсер, добавить тест, обновить README») не ловилась —
в списке были только повелительные формы, и гейт молчал. Добавлены инфинитивы
(собери/собрать, исправить, добавить, обновить, создать, проверить, …). Глаголы
считаются по совпадениям (три глагола в одном шаблоне = три сигнала), а не по числу
шаблонов. Тривиальные («покажи версию») — по-прежнему нет.

## 9.1: универсальный протокол задач и единая область действия

Два дефекта, найденных владельцем в живом парке агентов.

### 1. Грандмастер работал не у всех

Стоп-гейт выходил сразу, если в каталоге проекта нет `.omp/memory` (`if (!kitProject) return`). Из 25 столов реестр памяти был только у трёх — остальные сессии жили **без проверки формы ответа**, и владелец видел ровно это: «в каких-то сессиях грандмастер есть, в каких-то нет».

Теперь гейт действует в любой рабочей зоне владельца: каталог под `~/OMP/`, git-проект или каталог с `.omp`. Случайные каталоги (например `/tmp`) по-прежнему не трогаются — там гейт был бы шумом. Наличие реестра памяти влияет только на правило памяти (memory-ack), а не на факт проверки.

### 2. Протокол задач стал частью гейта

Универсальный протокол (анализ → To-Do с полями → безопасность → реализация → проверка → документация → критерии завершения) добавлен в гейт двумя проверяемыми правилами:

| Правило | Когда срабатывает | Что требует |
|---|---|---|
| Откат | статус `ГОТОВО`/`ГОТОВО-С-ОГРАНИЧЕНИЯМИ` и в сессии были `edit`/`write` | строку `ОТКАТ: <как вернуть исходное>` либо явное «изменения необратимы» / «откат не требуется» |
| Документация | то же и работа многошаговая (`edit`/`write` ≥ 2 или вызовов инструментов ≥ 12) | след документации: `TASK_PLAN.md`, `TASK_REPORT.md`, `JOURNAL.md` — или явное «документы не нужны: одна правка» |

Обе проверки читают **фактические вызовы инструментов** из сообщений сессии (`sessionWorkFrom`), а не заявления в тексте. Полный текст протокола — `~/.omp/agent/TASK_PROTOCOL.md`, краткая версия — в `APPEND_SYSTEM.md`.

Тесты: `bun test ~/.omp/agent/GRANDMASTER_8/tests/gm8.test.ts` (38 проверок, включая 9 новых на протокол).

## 10.0 — автономное доведение задачи до проверенного результата

Версия 9.1 закрывала обходы приёмки, но система допускала **преждевременное завершение на PARTIAL**:
исполнитель отчитывался, задача считалась законченной, и владелец вынужден был писать «продолжай».

Что исправлено:

| Переход | Было | Стало |
|---|---|---|
| `APPEND_SYSTEM.md` (anti-loop) | «три попытки без прогресса → отчёт PARTIAL/BLOCKED» — то есть завершение | меняй уровень (config → код → данные), читай диагностику, изолируй пробой, привлекай проверяющего — и продолжай; PARTIAL/BLOCKED не закрывают задачу |
| `TASK_PROTOCOL.md` | PARTIAL как терминальный статус | промежуточный результат; закрытие только проверенным результатом или явной отменой владельца |
| `loop-breaker` | после лимита блокировок гейт отпускал вызов — слепой повтор | повторение запрещено; исполнитель получает **историю попыток** и требование сменить действие |
| `stop-gate` | PARTIAL проходил, задача заканчивалась | PARTIAL/BLOCKED → состояние `needs-fix` с замечаниями и открытыми пунктами |

Новое в 10.0:

- `hooks/lib/task-state.ts` — устойчивое состояние задачи в `.omp/task-state.json`:
  цель, критерии, этап, открытые пункты, статус (`open | needs-fix | awaiting-external | verified | cancelled`),
  попытки, замечания, условие продолжения. Пишется атомарно под межпроцессным замком,
  переживает окончание ответа, смену исполнителя и перезапуск OMP.
- `bin/autonomy-loop.ts` — управляющий цикл: задача → выполнение → проверка → замечания →
  исправление → повторная проверка. Читает состояние, возвращает задачу исполнителю с
  фактическими замечаниями, останавливается только на `verified`, `cancelled` или
  `awaiting-external` (с условием продолжения).
- `hooks/lib/version.ts` — версия комплекта одним источником правды.

Живой прогон 2026-11-03: изолированный проект с настоящим дефектом (`sum()` без начального
значения), владелец дал задачу **один раз** → исполнитель от `omp-exec` сам исправил
(`reduce(..., 0)`), тесты 2/0, независимое ревью PASS, сертификат ГОТОВО, демон-верификатор PASS.
Ни одного «продолжай» между поручением и результатом.

Попутно живой прогон нашёл реальный дефект: хук наблюдателя спавнил `bun` по имени, а под
`omp-exec` его нет в PATH → расширение падало и прогон исполнителя умирал. Теперь
интерпретатор берётся из `process.execPath`.
