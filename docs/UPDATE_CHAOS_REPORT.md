# UPDATE_CHAOS_REPORT — OMP Pocket

Этап 4 программы. Изолированная среда: временный HOME, компилируемые фейковые бинари `omp/herdr/systemctl/git/bun`,
фейковый build-сервер (метаданные + SHA-256), фейковый шлюз `/api/health`. Живая система в экспериментах не
участвует — ни один сценарий не трогает production-сервисы.

Прогон: `cd gateway && bun test update/chaos` (файл `gateway/update/chaos/scenarios.test.ts`).
Каждый сценарий — отдельный тест; PASS/DONE фиксируется утверждениями по файлам состояния, журналу событий,
`/proc/<pid>/exe`, содержимому бинаря и промптам панелей.

## Что проверено по ресурсам и зависаниям

- Нет бесконечных повторов: у каждой внешней команды таймаут (`exec`), при срабатывании убивается дерево процессов;
  повторы фазы ограничены одной повторной попыткой восстановления.
- Нет зависших процессов: тесты проверяют, что после `BLOCKED`/`FAILED` панели не запускаются лишний раз;
  изолированные сессионные процессы убиваются в `afterEach`.
- Нет утечки «успеха»: `COMPLETED` ставится только после проверки работающих версий; `boot`-возобновление больше
  не помечает шаги `ok` без проверки.
- Секреты: бэкап конфигов пишется в артефакты задачи, в журнал событий содержимое конфигов не попадает.

## Гигиена прогона

- Каждый сценарий живёт в своём `/tmp/omp-chaos-<pid>-…`: после теста каталог удаляется, а процессы,
  чья командная строка указывает внутрь каталога (их спавнит и тест, и фейковый herdr), добиваются
  `killProcessesUnder` — иначе прогон копит сотни миров и сиротских процессов.
- Компилированные фейковые бинари кешируются в `/tmp/omp-chaos-cache` (`driver.bin`, `omp-<версия>.bin`),
  чтобы не собирать 90 МБ ELF на каждый тест.
- Один дублирующий прогон набора был оборван лимитом задачи (300 с) — это не провал теста: набор целиком
  прошёл отдельным запуском (32 сценария, 0 fail), полный `bun test` — 106 pass / 0 fail.

## Ограничения метода

- Фейковый `omp` — скомпилированный драйвер: проверка «работает новый бинарь» идёт по `/proc/<pid>/exe`, как в проде,
  но внутренние механики `--restore` реального omp эмулируются (продолжение турна проверяется промптом, а не
  доигрыванием внутри omp).
- Реальные телефон/сеть, реальная перезагрузка хоста и миграции БД не воспроизводились (см. UNVERIFIED).
- Живая проверка на настоящем стенде — `UPDATE_ACCEPTANCE.md`.
