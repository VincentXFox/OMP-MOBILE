# P0: Visual Gate и Deployment Gate

Два механизма, закрывающие два способа соврать: «интерфейс проверен» без браузера и «выложено» без приёмки и разрешения владельца.

## Роли и изоляция

| Роль | Что делает | Чем ограничена |
|---|---|---|
| IMPLEMENTER | пишет код, контракт, проверки | не может выдать PASS: гейт требует артефакты, а не строки |
| BROWSER RUNNER | `bin/visual-runner.ts` — браузерная матрица, скриншоты, DOM-проверки | подписывает пакет **своим** ключом (`~/.omp/visual-runner.ed25519`), гейт знает только публичный |
| REVIEWER | независимый разбор изменений | вердикт без провенанса (`evidence.kind`) не принимается |
| VERIFIER | `omp-verifier` — аттестат сертификата и **разрешения владельца** | ключ у сервиса; исполнитель может только попросить |
| DEPLOYER | `bin/deploy.ts` — единственная санкционированная выкладка | запускается только при `AUTHORIZED`, гасит разрешение через верификатор |

Ключи лежат под одним uid, поэтому полной изоляции на одной машине нет: настоящая граница — отдельный пользователь или внешний подписывающий сервис (см. «Остаток»).

## Visual Gate

### Что требуется

8 разрешений × 2 темы = **16 комбинаций**, по 3 скриншота (top/middle/bottom) — **48 PNG**, и пять DOM-проверок на комбинацию:

| Проверка | Что ловит |
|---|---|
| `overlap` | панель/шторка перекрывает контент или сетку |
| `lastBrand` | последний пункт списка брендов недостижим (скрыт, под шторкой) |
| `horizontalOverflow` | горизонтальная прокрутка страницы |
| `buttons` | «Показать N»/«Сбросить» не реагируют |
| `theme` | тема не применилась (фон не соответствует light/dark) |

Разрешения: 320×640, 320×844, 360×640, 360×844, 390×640, 390×844, 430×640, 430×844.

### Доказательства

`bin/visual-runner.ts` пишет `.omp/gate/<slug>/visual/evidence.json` + `evidence.sig` (Ed25519 по каноническому JSON) и `shots/*.png`. В пакете: URL стенда, commit, отпечаток `git diff HEAD`, `runId`, время, ключ раннера, Chrome, по каждой комбинации — пути, sha256 и размеры кадров, результаты пяти проверок.

### Что проверяет гейт (`bin/visual-gate.ts`, команда `quality-gate visual`)

| Условие | Статус |
|---|---|
| нет пакета/подписи | `UNVERIFIED` |
| подпись не подтверждена публичным ключом раннера | `BLOCK` |
| пакет подписан не тем ключом | `BLOCK` |
| sha256 кадра не совпал с файлом | `BLOCK` |
| скриншоты от другого commit | `BLOCK` |
| код менялся после прогона (`git diff HEAD`) | `BLOCK` |
| нет разрешения, одна тема, не хватает кадров | `BLOCK` |
| кадр пустой (< 1 КиБ) | `FAIL` |
| провалена любая DOM-проверка | `FAIL` |
| всё сошлось | `PASS` |

PASS общего сертификата невозможен: при `visual.required` `verify` добавляет «нет визуальной приёмки» или причину `VISUAL_GATE <статус>`.

## Deployment Gate

`bin/deploy-gate.ts` проверяет восемь условий одновременно:

1. `tests` — все проверки сертификата пройдены;
2. `visual` — Visual Gate = PASS (если контракт требует);
3. `review` — независимый вердикт с провенансом;
4. `attestation` — аттестат подтверждён верификатором;
5. `noFail` — статус сертификата `ГОТОВО` (нет FAIL/UNVERIFIED);
6. `commitMatch` — выкладываемый commit = HEAD;
7. `stagingQa` — `staging.json` на тот же commit;
8. `ownerApproval` — одноразовое разрешение владельца.

Итог: `AUTHORIZED` / `DENIED` (условие не выполнено) / `BLOCKED` (подделка, устаревание, попытка обхода). `AUTHORIZED` **не** означает «выложено».

### Разрешение владельца

Текстом агента не выдаётся. Порядок:

```bash
bun bin/deploy-gate.ts request <slug> --release ID --commit SHA --person "владелец"   # заявка
bun bin/deploy-gate.ts approve <slug> --release ID --commit SHA --person "владелец"   # подписывает верификатор
bun bin/deploy.ts --slug <slug> --release ID --commit SHA --approval ~/.omp/deploy-approvals/ID.json \
  --deployer-cmd '<команда DEPLOYER>' [--dry-run]
```

Разрешение привязано к `release`, `commit`, `env`, сроку и личности; `nonce` гасится в ledger сервиса при первом использовании, поэтому копия файла бесполезна. Для этого у демона добавлены действия `approve` и `check-approval` (`bin/verifier-daemon.ts`).

### Техническая изоляция выкладки

`deploy/hooks/pre/deploy-guard.ts` (устанавливается в `~/.omp/agent/hooks/pre/`) блокирует bash-команды, меняющие состояние прода: `scp/rsync/sftp/sshfs` к `194.58.95.216`/`lamplife.ru`, `docker exec|restart|compose`, `bench build|restart|clear-cache`, запись в `/srv/lamplife`. Чтение (curl GET, читающий ssh) не блокируется. Исключение — выкладка с `OMP_DEPLOY_AUTH=<release>`, подтверждённая верификатором; ошибка проверки трактуется как запрет (fail-closed).

## Негативные сценарии (тесты)

`bin/visual-gate.test.ts` (12 тестов) и `bin/deploy-gate.test.ts` (11 тестов) проверяют: ручной PASS, поддельный сертификат, отсутствие Visual QA, отсутствие согласия владельца, изменённый commit, устаревшую аттестацию, подмену скриншотов, прямое обращение к прод-хостам, повторное использование разрешения, недоступный верификатор.

## Состязательный разбор и что из него исправлено (27.10)

Независимый ревьюер нашёл 14 обходов; ключевые закрыты в этом же наборе:

| № | Находка | Исправление |
|---|---|---|
| 1 | гонка в ledger: одно разрешение гасилось 4 раза из 8 | погашение — атомарное создание файла-nonce (`open(…, "wx")`), успешен ровно один вызов |
| 2 | `approve` выдавал разрешение любому, кто дотянулся до сокета (самовыдача) | требуется **токен владельца** (`OMP_OWNER_TOKEN_FILE`, по умолчанию `/etc/omp-verifier/owner-token`, mode 600); без него — отказ |
| 3 | разрешение переносилось на другой release/commit/env | демон сверяет `release`, `commit` и `env` |
| 4 | `cert.visual` не попадал в сертификат — оба гейта считали, что визуальная приёмка не нужна | `run` переносит `visual` из контракта; добавлен регрессионный тест |
| 5 | якорь доверия выбирал сам проверяемый процесс (`OMP_VISUAL_RUNNER_PUB`, `--pub`) | отпечаток ключа раннера **закрепляется в контракте** (`init --visual-key`), пакет с другим ключом отвергается |
| 6 | пакет не был привязан к slug и стенду | сверяются `evidence.slug` и URL из контракта |
| 7 | без git привязка к commit молча выключалась (fail-open) | нет commit — `BLOCK` |
| 8 | `staging.json` — самодельный файл | его хеш входит в проверку аттестата: правка после аттестации ломает связь |
| 9 | «провенанс» ревью принимал любую строку | белый список `spawn`/`attestation` |
| 10 | `docker-compose` не ловился | регулярное выражение покрывает оба написания |
| 11 | обходы `tee`/`dd`/`sed -i`/`cp`/`install`/`curl -X POST`/`ansible` | логика перевёрнута: любое обращение к проду без распознанного чтения — запрет (fail-closed) |
| 12 | `--dry-run` сжигал одноразовое разрешение | предпросмотр ничего не гасит |
| 13 | скачивание с прода блокировалось как запись | направление «прод → локально» разрешено |
| 14 | `keyId` расходился из-за хвостового перевода строки в `.pub` | PEM нормализуется так же, как у раннера |

Регрессии: `bin/p0-hardening.test.ts` (14 тестов) воспроизводит каждую находку и требует отказа.

## Внедрение (после разрешения владельца)

1. Влить ветку `p0/gates` в `master` и запушить.
2. Установить хук: `install -m 644 deploy/hooks/pre/deploy-guard.ts ~/.omp/agent/hooks/pre/deploy-guard.ts`.
3. Перезапустить `omp-verifier`, чтобы у него появились действия `approve` и `check-approval` (сервисный файл уже указывает на `bin/verifier-daemon.ts`).
4. Создать токен владельца: `install -m 600 /dev/null /etc/omp-verifier/owner-token` (или путь из `OMP_OWNER_TOKEN_FILE`) и записать в него случайную строку — только владелец; без него разрешения не выдаются.
5. Создать ключ раннера: `bun bin/visual-runner.ts --url … --slug smoke --out /tmp/smoke` (ключ создастся сам, mode 600) и убедиться, что публичный `~/.omp/visual-runner.ed25519.pub` доступен гейту.
6. В проектах с интерфейсом — `quality-gate init … --visual-required --visual-url <стенд> --visual-key ~/.omp/visual-runner.ed25519.pub --visual-covers AC-XX`.

## Откат

- Хук: удалить `~/.omp/agent/hooks/pre/deploy-guard.ts`.
- Верификатор: вернуть прежний `bin/verifier-daemon.ts` и перезапустить сервис (действия `approve/check-approval` исчезнут, разрешения перестанут выдаваться — выкладка станет невозможной, что безопасно).
- Ветку не вливать: `git worktree remove /tmp/gm-audit/p0` и `git branch -D p0/gates`.

## Остаток

1. Ключи раннера, верификатора и исполнителя живут под одним uid: компромат исполнителя даёт доступ к подписи раннера и к токену владельца, если тот лежит в его домашнем каталоге. Настоящая граница — отдельный uid для раннера/верификатора и токен владельца вне дома исполнителя (по умолчанию так и есть: `/etc/omp-verifier/owner-token`).
2. Хук ловит выкладку через bash; вызовы не через bash (например, GUI-инструменты) он не видит.
3. `overlap` и `buttons` — эвристики по селекторам конкретной витрины; при смене вёрстки их нужно править вместе с сайтом.
4. Аттестация и разрешения требуют работающего `omp-verifier`; при его недоступности гейт честно отказывает (`DENIED`), а не пропускает.
