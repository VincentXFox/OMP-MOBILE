# Файловое дерево агентских процессов

Логика процессов — это каталоги и текстовые файлы, а не код фреймворка. Идея из доклада «agent architecture as folders» (Jake Van Clief): агент маршрутизируется к трём вещам — **что делать** (промпт), **чем** (инструмент), **на чём** (данные), и всё это лежит в дереве, которое видно глазами и правится в редакторе.

## Зачем это здесь

Фреймворк-оркестратор требует кода на каждую новую ветку. Дерево требует папки. Когда провайдер выпускает нативную фичу, шаг **сжимается** до инструмента, а не переписывается `Workflow`-класс. Плюс всё, что делает агент, остаётся проверяемым: результат шага — файл, а не «модель сказала, что готова».

## Структура

```
workflows/
├── AGENTS.md            # роутер: как ходить по дереву
├── .mcp.json            # внешние источники данных (MCP)
├── _template_task/      # заготовка шага: копируется для новых задач
│   ├── prompts/instructions.md
│   ├── tools/
│   └── data/{input,output,schema.json}
└── <процесс>/
    ├── WORKFLOW.md      # цель, маршрут, условия перехода
    ├── _template_task/  # своя заготовка шага
    ├── 01-<шаг>/
    │   ├── prompts/instructions.md   # читается при входе в шаг
    │   ├── tools/                    # детерминированные скрипты шага
    │   ├── data/{input,output}
    │   ├── data/schema.json          # форма результата
    │   ├── task.json                 # kind: task | tool
    │   └── subtasks/<подзадача>/…    # независимые ветки для субагентов
    └── 02-<шаг>/…
```

Правило, на котором держится вся схема: **результат шага — файл в `data/output/`**. «Сделано» без файла не считается; следующий шаг проверяет наличие и валидность этого файла.

## Инструмент

```bash
bun ~/omp-mobile/bin/agent-tree.ts init                 # AGENTS.md, .mcp.json, _template_task
bun ~/omp-mobile/bin/agent-tree.ts new-workflow release --goal "…"
bun ~/omp-mobile/bin/agent-tree.ts new-task release 01-check --prompt "…" [--subtasks api,ui]
bun ~/omp-mobile/bin/agent-tree.ts new-subtask release/01-check ui --prompt "…"
bun ~/omp-mobile/bin/agent-tree.ts list [--json]
bun ~/omp-mobile/bin/agent-tree.ts lint [--json]        # exit 1 при проблемах
```

Правила адаптации из доклада (§5) — командами, а не переписыванием кода:

| Ситуация | Команда | Что происходит |
|---|---|---|
| Провайдер дал нативную фичу, шаг стал одним вызовом | `collapse-task <процесс>/<шаг> --note "причина"` | `task.json` → `kind: tool`, подзадачи уходят в `_subtasks-archived/`, в инструкцию дописывается пояснение; маршрут и данные остаются |
| Целый процесс теперь выполняется за шаг | `demote-workflow <процесс> <получатель>/<шаг>` | папка процесса переносится в `subtasks/` шага-получателя |

Линтер проверяет: `WORKFLOW.md` с разделами «Цель»/«Маршрут», `_template_task` на месте, у шага есть `prompts/instructions.md`, `data/input`, `data/output`, валидный `schema.json`; шаг без `tools/` допустим только если это шаг-рассуждение с подробной инструкцией (400+ символов).

## Как это попадает в агента

Хук `~/.omp/agent/hooks/pre/agent-tree-router.ts` на `before_agent_start`:

1. поднимается от `cwd` вверх, пока не найдёт узел дерева (`AGENTS.md` с роутером, `WORKFLOW.md` или `task.json`) — случайный `AGENTS.md` проекта деревом не считается;
2. собирает карточку: цель и маршрут процесса, инструкция текущего шага, состав `tools/`, входы/результаты, подзадачи (их отдают субагентам папками), соседние шаги с отметкой «есть результат»;
3. добавляет блок `<<<AGENT-TREE …>>>` в системный промпт — не больше 2200 символов, повторно в той же сессии не повторяется (sha256);
4. любая ошибка — fail-open.

Вне дерева хук молчит: обычные проекты работают как раньше.

## В PWA

`GET /api/tree` обходит корни (`~/OMP/workflows` и всё из `OMP_TREE_ROOTS`) и возвращает процессы, шаги с их `tools/inputs/outputs`, подзадачи и результат линтера. Экран «Проекты» показывает секцию «Воркфлоу»: прогресс по шагам, бейдж проверки структуры, состав инструментов и подзадачи.

## Живой пример

`~/OMP/workflows/omp-pocket-release/` — выпуск OMP Pocket за четыре шага:

| Шаг | Инструмент | Что даёт |
|---|---|---|
| `01-check` | `tools/check.ts` | health шлюза, версии компонентов, статус обновления, systemd-юниты → `check.json` |
| `02-build` | `tools/build.ts` | типы обоих пакетов, сборка PWA, тесты (полный режим) → `build.json` |
| `03-verify` | `tools/verify.ts` | публичный health, WebSocket до релея, число сессий, граф памяти → `verify.json` |
| `04-report` | `tools/report.ts` | сведённый отчёт с явным «нет результата», если шаг провалился → `REPORT.md` |

Прогон целиком — четыре команды `bun`, без оркестратора и без фреймворка.

## Границы

- Хук читает файлы и ничего не проверяет исполнением: соответствие `schema.json` держится на инструменте шага и линтере, а не на модели.
- Роутер не запрещает править файлы вне шага — он только даёт маршрут; жёсткие запреты живут в обычных гейтах (todo-first, stop-gate).
- Дерево — про процессы, а не про хранение знаний: факты и решения проекта живут в графе памяти (`docs/GRAPH_MEMORY.md`).
