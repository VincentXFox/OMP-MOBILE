# AGENT_QUALITY_GATE

**Доказательная приёмка работы AI-агента: CONTRACT · BASELINE · EVIDENCE · ADVERSARIAL · REGRESSION · CHAOS · INVARIANTS · OBSERVABILITY · ROLLBACK · RESIDUAL · INDEPENDENT REVIEW**

> `DONE = доказанная работа, а не написанный код.`
>
> Агент не вправе объявить работу законченной на основании собственного утверждения, зелёного билда или отсутствия явной ошибки. Статус `ГОТОВО` допустим только при выполненных критериях приёмки и воспроизводимых доказательствах.

## Зачем это нужно

Без формальной проверки агент может: заявить «исправлено», проверив только исходник; объявить обновление успешным, хотя обновился бинарник, а процесс остался старым; починить одно и сломать другое; принять на веру автопроверку, которая молча не запускалась; скрыть неудачу за «всё работает».

Реальный случай из практики этого стенда: юнит `omp-post-boot-check.service` выглядел исправным, был `enabled`, а после перезагрузки не запускался вовсе — `systemd` срезал задачу из-за цикла упорядочивания. Отчёт «всё готово» был бы ложью; обнаружилось только потому, что доказательство (файл `POST-BOOT.md`) отсутствовало.

## Разница между двумя главными маркерами

- `EVIDENCE` — доказательство, что ожидаемое поведение наблюдалось: `проверка → фактический результат`.
- `ADVERSARIAL` — попытка доказать, что решение ошибочно: `гипотеза о сбое → провокация сбоя → наблюдение → вывод`.

Если проверка не запускалась, агент **не имеет права** выдавать ожидаемую строку за фактическую.

## Механизмы

| Механизм | Назначение | Минимум для отчёта |
|---|---|---|
| `CONTRACT` | измеримые критерии приёмки и границы задачи | список `AC-01…`, критичность |
| `BASELINE` | фактическое состояние до изменения | команда → значение до |
| `EVIDENCE` | проверка каждого критерия | `EVIDENCE [AC-XX]: действие → вывод` |
| `ADVERSARIAL` | поиск ложного успеха | гипотеза → провокация → результат |
| `REGRESSION` | защита существующего поведения | смежные проверки → результат |
| `CHAOS` | отказы и восстановление | контролируемый сбой → восстановление |
| `INVARIANTS` | незыблемые условия | инвариант → метод → соблюдён |
| `OBSERVABILITY` | реальное состояние после изменения | службы, логи, метрики, ошибки |
| `ROLLBACK` | путь возврата | точка → действие → `TESTED/PLANNED/UNAVAILABLE` |
| `RESIDUAL` | честный остаток | непроверенное, дефекты, риски |
| `INDEPENDENT REVIEW` | проверка не тем, кто делал | вердикт отдельного агента/процесса |

### Форматы строк

```text
CONTRACT [AC-01]: <проверяемое требование> / метод / порог / blocking|non-blocking
BASELINE: <команда> → <фактический результат до изменения>
EVIDENCE [AC-01]: <что выполнил> → <фактический вывод>
ADVERSARIAL: <гипотеза о сбое> → <провокация> → <наблюдение>
REGRESSION: <смежные сценарии> → прошло/упало, какие
CHAOS: <внесённый сбой> → <восстановление> → <потери/дубликаты>
INVARIANTS: <условие> → <проверка> → <соблюдён/нарушен>
OBSERVABILITY: <где и за какой интервал> → <ошибки/значения>
ROLLBACK: <точка возврата> → <как вернуть> → TESTED/PLANNED/UNAVAILABLE
INDEPENDENT REVIEW: <кто проверял независимо> → PASS/FAIL + свои доказательства
RESIDUAL: <что не проверено> → причина и влияние
```

## Правила

1. Не выдумывать выводы команд, тестов, логов и скриншотов.
2. Запланированная проверка ≠ выполненная. Зелёный юнит-тест не доказывает end-to-end поведение.
3. Каждый обязательный критерий имеет собственное доказательство из целевой среды.
4. Доказательство подтверждает именно заявленное, а не слабый прокси: `omp --version` доказывает версию CLI, но не версию работающего демона.
5. Проверять и успешный, и отказный путь; специально искать ложноположительный успех.
6. После последней правки — перепроверка затронутых критериев; предыдущее доказательство устаревает.
7. Нельзя понижать критерии, ослаблять пороги, помечать обязательное необязательным и «прощать» падения молча. Смена требований — только с явной фиксацией новой версии контракта.
8. Критические инварианты сохраняются: данные, секреты, подтверждения опасных действий, административный доступ.
9. Разрушительные CHAOS-проверки — только в согласованной среде или с разрешённым планом; на живой системе без разрешения нельзя.
10. `TESTED` откат отличается от `PLANNED`; «откат предусмотрен» не равно «откат проверен».
11. Любой проваленный обязательный критерий запрещает `ГОТОВО`.
12. Непроверенные обязательные критерии → `PARTIAL`/`ГОТОВО-С-ОГРАНИЧЕНИЯМИ`, не `ГОТОВО`.
13. Неприменимая проверка помечается `N/A` с причиной; `N/A` ≠ `PASS`.
14. Внешняя преграда → `BLOCKED` с `БЛОКЕР:` и списком испробованных стратегий.
15. Отчёт краткий, но достаточный для независимого воспроизведения. Никакой церемонии ради церемонии.

## Статусы

| Статус | Условия |
|---|---|
| `ГОТОВО` | все обязательные критерии доказаны, инварианты соблюдены, блокирующих дефектов нет |
| `ГОТОВО-С-ОГРАНИЧЕНИЯМИ` | работа сделана, но часть критериев физически недостижима — с тегом причины `[железо]`/`[чужие-доступы]`/`[нужно-согласие]`/`[провайдер]`/`[физически-нет]` и строкой «пробовал: … → результат» |
| `PARTIAL` | часть объёма доказана, обязательные пункты не закрыты; указаны объём и границы |
| `BLOCKED` | нужен `БЛОКЕР:` + ≥2 испробованные стратегии |

## Что проверяет машина

Стоп-гейт (`grandmaster-stop-gate.ts`) блокирует финал, если для `ГОТОВО`/`ГОТОВО-С-ОГРАНИЧЕНИЯМИ` нет строк `CONTRACT:`, `EVIDENCE:`, `REGRESSION:`, `INVARIANTS:`, `RESIDUAL:`; а если в ответе заявлена рискованная работа (живая система, обновление, выкатка, миграция, перезагрузка) — дополнительно `BASELINE:`, `OBSERVABILITY:`, `ROLLBACK:` и `REVIEW:`.

Хук `grandmaster-adversarial-review.ts` требует `ADVERSARIAL:` с независимой проверкой (`reviewer`/`security-reviewer`/`gm-harness`).

## Минимальный и полный набор

- Обычная задача: `CONTRACT + EVIDENCE + ADVERSARIAL + REGRESSION + INVARIANTS` (+ `RESIDUAL`).
- Сложная или рискованная: добавить `BASELINE + OBSERVABILITY + ROLLBACK + RESIDUAL + INDEPENDENT REVIEW`, при необходимости `CHAOS`.

## Независимая приёмка

```text
BUILDER  → реализует и даёт доказательства
SKEPTIC  → ищет контрпримеры
VERIFIER → воспроизводит критерии приёмки
GATE     → ГОТОВО / PARTIAL / BLOCKED
```

Ревьюер не принимает фразу «всё работает» как основание: ему нужны артефакты и, по возможности, независимые black-box проверки. Для мелких задач роли можно пройти последовательно одним агентом — но тогда в отчёте прямо пишется, что независимость ниже.

## Запрещённые подмены

| Подмена | Почему недопустима |
|---|---|
| «Код написан» вместо «работает» | Наличие реализации не доказывает поведение |
| «Тесты зелёные» без вывода | Неизвестно, что именно проверено |
| `HTTP 200` вместо проверки тела | Внутри может быть логическая ошибка |
| Модуль «enabled» вместо «запустился» | Единица может быть срезана при загрузке (реальный случай выше) |
| «Логов с ошибками нет» без интервала и источника | Неизвестен охват наблюдения |
| «Откат предусмотрен» | План не равен испытанному восстановлению |
| «Всё готово, кроме…» | Если «кроме» — обязательный критерий, это не `ГОТОВО` |
| «Я сам себя проверил» как независимая экспертиза | Self-review полезен, но не эквивалентен |

**Итог:** ошибиться и честно об этом сказать — право. Маскировать неудачу под успех — нет. Доказанный `PARTIAL` лучше выдуманного `ГОТОВО`.
