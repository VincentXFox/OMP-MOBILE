# Автономные задачи (autonomy)

Серверный управляющий цикл: пользователь задаёт цель один раз, дальше шлюз сам
продолжает работу, проверяет результат и останавливается по делу — без «продолжай»
из чата и без того, чтобы телефон вообще был подключён.

## Из чего состоит

| Файл | Роль |
|---|---|
| `types.ts` | Task, статусы, критерии, доказательства, попытки, бюджет, pendingAction |
| `store.ts` | Дамп задач в `gateway/tasks/<id>.json`, атомарная запись (tmp+rename), чтение с диска |
| `links.ts` | Контракт `AgentLink` + `ScriptedLink` (сценарный двойник для тестов) |
| `rpc-link.ts` | Настоящая связь: `omp --mode rpc-ui --approval-mode always-ask` как дочерний процесс, NDJSON, approvals, дельта usage |
| `checks.ts` | Проверки приёмки: команда + правило успеха, журнал EVIDENCE, точечный и полный прогон |
| `budget.ts` | Учёт токенов (вход/выход/кэш) и денег, резерв на финальную проверку |
| `controller.ts` | Сам цикл: план → ход → проверки → решение о прогрессе → продолжение/стоп |

## Критерии приёмки

Два режима:

1. **Заданы автором** (рекомендуется): `criteria[].check.command` — то, что реально
   проверяет результат. Набор копируется в задачу и гасится (`passed=false`) до первого
   действия, модель его не меняет и не может «заранее закрыть».
2. **Выводятся из цели**: если `criteria` пустой, контроллер делает один плановый ход
   с требованием вернуть JSON `{"criteria":[{id,statement,check:{command}}]}`,
   валидирует его (1–6 критериев, у каждого непустая команда), помечает `derived: true`
   и фиксирует ДО первого рабочего действия. Не разобралось — задача встаёт в `blocked`
   с прямым текстом «задай критерии явно», а не идёт работать вслепую.

## Жизненный цикл

```
POST /api/tasks (цель + критерии + бюджет)
        │
        ├─ criteria[] пишутся в задачу ДО первого действия (passed=false)
        ▼
   queued → running ──(модель сделала ход)──→ verifying (точечный прогон)
        ▲                                          │
        │        прогресс есть, критерии открыты   │
        └──────────────────────────────────────────┘
                                                   │ все критерии открыты → полный прогон
                                                   ▼
                                                 done
```

Остановки, которые не являются успехом: `blocked` (нужен внешний шаг/доступ),
`budget_exhausted`, `no_progress`, `paused`, `cancelled`, `failed`. Успех — только
`done`, и только после того, как зелёными стали **проверки**, а не текст модели.

## Управляющие параметры

| Параметр | Где | Смысл |
|---|---|---|
| `noProgressThreshold` | `ControllerDeps` (по умолчанию 3) | Сколько ходов без нового закрытого критерия допустимо до требования сменить стратегию |
| `strategiesBeforeStop` | `ControllerDeps` (по умолчанию 2) | Сколько новых стратегий пробуем после порога; дальше — `no_progress` |
| `maxTokens` | `budget` задачи | Жёсткий лимит токенов (вход+выход+кэш); считается по данным omp |
| `reserveTokens` | `budget` задачи | Недоступный для работы резерв: тратится только на финальную приёмку |
| `maxCostUsd` | `budget` задачи | Денежный лимит; работает, когда рантайм отдаёт стоимость (`get_session_stats.cost`) |
| `autoApprove` | задача | Шаблоны (`bun test*`) действий, которые не паркуют задачу на разрешение |

## Состояние и восстановление

- Каждый переход пишется на диск **до** следующего шага; задача сериализуема целиком.
- Перед ходом ставится `pendingAction`: после падения шлюза видно, что действие могло
  уйти в модель. Такой ход **не повторяется вслепую** — задача становится `blocked` с
  причиной «исход неизвестен, нужно подтверждение» (дешёвый идемпотентный случай —
  проверки — повторяется свободно).
- `resumeAfterRestart()` поднимает `running`/`verifying`/`queued`/`awaiting_approval`
  при старте шлюза; повторный вызов не создаёт второй цикл.
- Один цикл на задачу: `start(id)` идемпотентен, состояние задач хранится вне процесса.
- Закрытие телефона ничего не останавливает: задачи живут в шлюзе, UI только читает.

## Разрешения

`omp` запускается с `--approval-mode always-ask`, поэтому `write`/`exec` требуют
approval. Контроллер получает запрос через RPC, сверяет с `autoApprove`; что не
разрешено — паркует задачу в `awaiting_approval` (в UI видно заголовок, детали и две
кнопки). `deny` → `blocked` с причиной, `allow` → работа продолжается. Разрешение
привязано к конкретному действию (текст команды/пути), а не к «модели вообще».

## Проверки приёмки

```json
{"id":"c1","statement":"эндпоинт отвечает 200","check":{"command":"curl -sf localhost:8088/api/health","expectExit":0,"expectContains":"\"ok\":true"}}
```

- Правило успеха: код выхода (по умолчанию 0), `expectContains`, `expectAbsent`, таймаут (120 с).
- После хода — точечный прогон открытых критериев; перед завершением — полный набор.
- Каждая проверка пишет EVIDENCE: команда, код, хвост вывода, время. UI показывает
  «проверено: …» из **последнего зелёного** результата, а не из слов агента.
- Критерий без машинной проверки автоматически не закрывается: он требует ручной
  оценки и не может «пройти» молча.

## Бюджет и деньги

Токены берутся из `get_session_stats` (омп считает вход, выход, reasoning, cacheRead,
cacheWrite), деньги — из поля `cost` того же ответа: своя таблица цен не нужна и не
угадывается. Если стоимость недоступна, `spend.costUsd = null`, и это честно видно.
Встроенный `token_budget` goal-режима не используется как денежный лимит: он не
учитывает cache-read и допускает перелёт за границу одним ходом.

## Почему RPC, а не SDK и не TUI-панель

| Вариант | Почему нет |
|---|---|
| TUI через herdr-панели (как сейчас управляет телефон) | Управление текстом в терминале: нет структурированного расхода, approvals приходят как экранный текст, восстановление после рестарта ненадёжно |
| SDK в процессе шлюза | Тянет `@oh-my-pi/pi-coding-agent` в шлюз и связывает его версию с установленным omp; для управления задачами не нужен доступ к внутренностям сессии |
| **RPC (`omp --mode rpc-ui`)** | Официальный протокол установленной версии: ready/response/event кадры, `prompt`/`abort`/`get_state`/`get_session_stats`, approvals через `extension_ui_request`, изоляция в отдельном процессе |

## Тесты

```bash
cd ~/omp-mobile/gateway
bun test autonomy/tests            # controller (11) + scenarios §7 (9) + rpc-link (7)
```

- `controller.test.ts` — цикл: прогресс, стратегии, бюджет, approvals, отмена, рестарт.
- `scenarios.test.ts` — восемь сценариев приёмки из ТЗ пользователя на управляемых
  ответах модели и настоящих shell-проверках.
- `rpc-link.test.ts` — протокол на подставном «omp»-скрипте: корреляция по id, сборка
  хода, дельта usage, round-trip approval, abort, close.

## Что выяснилось на живом omp 18.10.4 (не по документации)

- **stdin ≠ стоп.** Документация обещает «stdin закрыт → exit 0»; фактически простаивающий
  `rpc-ui` процесс живёт дальше и жрёт CPU. Поэтому `close()` идёт с эскалацией: закрыть
  stdin → 5 с ожидания → `SIGKILL` группы. После завершённого хода процесс выходит сам (код 0),
  после простоя — 137.
- **Стоимость хода приходит** в `get_session_stats.cost` (живой пример: `$0.000448` за ход с
  bash); токены — `tokens.{input,output,cacheRead,cacheWrite}`. Отдельного usage в `agent_end`
  нет, запасной источник — `message.usage` ассистентских сообщений. `contextUsage.percent` — доля.
- **Approval-кадр:** `method:"select"`, многострочный `title: "Allow tool: bash\nCommand: …"`,
  `options:["Approve","Deny"]`. `read` разрешений не просит даже в `always-ask` — спрашивает
  `bash` и мутирующие инструменты.
- **Первый ход медленный:** старт ~70 с после admission, простой ход с `bash` — до 125 с.
  Поэтому таймаут хода по умолчанию 15 минут, снижать нельзя; `prompt` отвечает `agentInvoked`
  раньше событий, ждать нужно `prompt_result` по тому же `id`.

## Ограничения (честно)

- Гейты работают с **формой** доказательств: зелёная команда действительно запускалась,
  но критерий может быть сформулирован слабо — за качество формулировки отвечает тот,
  кто ставит задачу.
- «Одна задача — один процесс omp»: параллельные задачи возможны, но каждая жрёт свой
  процесс и своё контекстное окно.
- Модель может «закрыть» критерий, сделав ровно то, что проверяет команда, и не больше —
  это свойство любой проверки, а не дефект цикла.
- `maxCostUsd` действует, только если провайдер отдаёт стоимость; иначе бюджет — по токенам.
